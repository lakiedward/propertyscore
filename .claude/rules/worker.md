# Worker rules: SmartCheck scoring engine and document jobs

`worker/` is the trusted backend that runs outside Supabase (decision D20): the monthly SmartCheck snapshot builder and the online report generation today, the PDF job later. It is a pnpm workspace package (`@propertyscore/worker`) deployed to Railway from `worker/Dockerfile`. Everything in `CLAUDE.md` still applies (no comments, no secrets in the frontend, migrations only, tests only on request); the React, i18n and styling rules do not.

## Runtime and layout

- Node 24 runs the TypeScript directly (type stripping): no build step, imports end in `.ts`, only erasable syntax (`erasableSyntaxOnly`), no `enum`, no parameter properties, no namespaces.
- `src/main.ts` is the only entry; it reads `parseCommand` from `src/cli.ts` and dispatches. A new job is a new command there, never a second entry file.
- Configuration comes only from `readEnv()` in `src/config/env.ts` (Zod). A new variable goes into its schema, into the Railway service and into the PR description in the same change. Error messages name the variable, never its value.
- Logs are JSON lines through `createLogger` from `src/lib/logger.ts`, with ids and counts only: never addresses, emails, tokens or the database URL.
- Failures throw `WorkerError(code, message)`; the code (`snake_case`, at most 80 characters) is what reaches `score_snapshots.error_code`. Postgres functions raise codes with `errcode = 'P0001'`, which `errorCode()` passes through.

## Walking routing

- Walking times come from a self-hosted Valhalla service (`VALHALLA_URL`), built from the same Geofabrik extract. It runs as its own Railway service from the official Valhalla image, never inside `worker/Dockerfile`; the worker only calls its HTTP API. Locally: `docker run -p 8002:8002 -v $PWD/valhalla:/custom_files -e tile_urls=https://download.geofabrik.de/europe/romania-latest.osm.pbf ghcr.io/valhalla/valhalla-scripted:3.9.1`, then `VALHALLA_URL=http://localhost:8002`.
- Modules receive the client as `context.router` (`null` when `VALHALLA_URL` is unset). A module that walks calls `computeWalkAccess` with its own targets (`key`, `poiCategories`, `searchRadiusM`, `maxCandidates`) instead of routing itself. A module whose targets are not points of `poi_features` (park outlines, Safety elements) lists its own candidates with a `private` function returning the same `cell_id, lng, lat, candidates` shape and routes them with `walkCellCandidates`; without a router it records `distance_method: 'straight_line'` and the straight line times `walk_detour_factor`.
- Walking speed is `params.<key>.walk_speed_kmh`, passed to Valhalla as the pedestrian `walking_speed`; car times use `costing: 'auto'` on the same client.
- Neighbour smoothing uses `smoothScores` and `listNeighbourPairs` from `src/scoring/smoothing.ts` (backed by `private.grid_cell_neighbours`); percentiles against the city use `private.cell_score_percentile`.

## Transit routing (Python)

- `worker/transit/route.py` is the only Python in the worker: an r5py (R5, Java 21) job the accessibility module runs as a subprocess, like `osmium`. It reads a `job.json` (OSM clip, GTFS archives or folders, reference date and window, origins, stops, destinations) and writes `walk_stops.csv`, `destinations.csv`, `itineraries.csv` and `matrix.bin` (big-endian `uint16` minutes, `65535` = not reachable). `itineraries.csv` (walk, wait and ride per destination) and `itinerary_legs.csv` (the path of each leg of that trip as `[lng, lat]` pairs, `trip` `best`, plus `walk` for the walking-only option) are filled only when the job sets `itineraries`: r5py plans each pair on its own at about 2 s a pair, so the monthly snapshot leaves it off and saves the OSM clip (the city's coverage widened to take in its key destinations, such as an airport outside the city) and GTFS archives it routed on in `private.transit_routing_bundles` (older bundles of failed or superseded snapshots are dropped). The report's accessibility section reruns the job for the exact address (one origin, no matrix, `itineraries` on) on that saved network, about 30 to 60 s; every reachable destination is planned, so each one gets `path` in `result.accessibility.destinations[]` (legs with `mode` `walk` or `transit`, the line and the coordinates along the streets and the line; the walking option for a destination that is faster on foot), which the report draws instead of a straight line; if the bundle is missing or the job fails it keeps the cell's times without the breakdown. It never connects to the database; TypeScript reads its outputs and writes the rows.
- Its dependencies are pinned in `worker/transit/requirements.txt` and installed into the `/opt/transit` venv of the image, whose `bin` comes first on `PATH`, so the module calls `python3`. Java comes from the `eclipse-temurin:21.0.12_8-jre-noble` stage (an exact tag, bumped on purpose) of the `Dockerfile`; the R5 jar is downloaded and checksum-verified by r5py at build time into `XDG_CACHE_HOME`.
- The JVM is capped with r5py's `--max-memory 60%` (`R5_MAX_MEMORY` in `routing.ts`, passed as `r5py_arguments` in the job), leaving the rest of the container's RAM to Node and postgres.js. Size the Railway service from the largest city: the cell-to-cell matrix of București (~6,700 cells) is about 90 MB on top of the R5 network.
- Only pure helpers live outside `run()`, and they are tested with the standard library (`python3 -m unittest discover --start-directory worker/transit`), so CI needs no Java for them.

## Database access

- The worker connects with `DATABASE_URL` (the direct connection or the session pooler of the Supabase project, never the transaction pooler) as a role that can use the `private` schema. It is a secret: Railway variables only.
- SQL lives in `*.db.ts` files or in the score module, as tagged postgres.js queries with parameters; never string concatenation. JSON goes in with `sql.json(value)` and is unpacked with `jsonb_to_recordset` for bulk writes.
- Heavy geometry belongs in PostGIS functions in `private` (created by a migration, tested with pgTAP); TypeScript orchestrates and computes formulas that are easier to test in code.
- Supabase caps every statement of the `postgres` role at 2 minutes, and the session pooler does not forward a `statement_timeout` sent at connection time. A query that works on a whole city (a `private` function over its cells, a cursor over cells whose batches wait for routing, a city-wide delete) runs through `withLongStatements(sql, (transaction) => …)` from `db/sql.ts`, which sets `statement_timeout` to `LONG_STATEMENT_TIMEOUT` (3 hours) for that transaction only. The timeout of a cursor covers its whole life, including the routing between batches, so it is the routing budget of a city. Run the queries in the callback on the transaction it passes (with `transaction.json(...)`), except the writes inside a loop over a cursor opened on that transaction: postgres.js runs one query at a time per connection, so a write on the same transaction waits behind the suspended cursor forever; those writes go through `sql`.
- The engine schema is `private`, never exposed to PostgREST. Tables there still get RLS enabled, no client policies, and a pgTAP test proving `anon` and `authenticated` cannot read them.

## Data model the scores share

| Table | What a score does with it |
| --- | --- |
| `public.cities` | the 9 cities with `boundary` (the coverage area the grid covers); read only |
| `public.scoring_versions` | the active `online` formula: `weights` (the 9 category weights) and `params` (`cell_size_m` plus one object per score key, for example `params.green`); a version used by a snapshot is frozen, so a formula change is a new version |
| `public.score_snapshots` | one row per monthly build; `source_dates` and `stats` are written by the orchestrator |
| `private.grid_cells` | hexagons built with `ST_HexagonGrid` in EPSG:3844, key `size:i:j`, stable across snapshots; `private.grid_cell_neighbours(city_id, size_m)` returns each cell with its (up to 6) touching neighbours, for smoothing |
| `private.cell_scores` | one row per cell and snapshot; a score writes `categories.<key>` (0–100 or `null` for no data) and `inputs.<key>` (the audit trail) through `writeCategoryScores` |
| `private.poi_features` | points of interest frozen per snapshot, `category` in `snake_case`, `source_ref` such as `osm:node/123`; `area` holds the outline of points that are areas (parks), and walking targets use its point closest to the origin |
| `private.residential_areas` | OSM `landuse=residential` per snapshot; `private.mark_residential_cells` sets `cell_scores.is_residential` when at least `params.residential_min_share` of the cell is residential, and leaves it `null` (counted as residential) for a city without that data |
| `private.cell_walk_access` | per snapshot, cell and walking category: `t_nearest_s`, `d_nearest_m`, cumulative `n5`/`n10`/`n15`, `nearest_poi_id`, `distance_method`; written by `computeWalkAccess` |
| `private.city_category_stats` | per snapshot, city and walking category: `poi_count`, `is_covered` (enough points to score the category in that city), city average time and share of cells within 15 minutes |

The orchestrator computes `overall` (weighted mean of the categories that have data, `private.compute_overall_scores`) and `stats.cities.<slug>` (cells, residential cells, and per category `scored`, `no_data`, `avg` over residential cells, a 20-bin `histogram`) after every module ran. A score that needs extra city figures writes them under `stats.<key>` itself.

## Adding a score

1. Migration for the score's own tables in `private` (for example `private.green_areas`), each with `snapshot_id` when the data is frozen per snapshot, GiST indexes on geography columns, RLS enabled, and its pgTAP test. Add the score's parameters to `params.<key>` of the formula version in the same migration (or a new version if the current one is already used).
2. `src/scoring/<key>/<key>.formula.ts`: pure functions from measured values to component points (`linearPoints`) and the score (`weightedScore`), with a `*.test.ts` that reproduces the plan's worked example.
3. `src/scoring/<key>/<key>.module.ts`: exports a `ScoreModule` with `key` and `run(context)`. `run` parses `context.params` with a Zod schema (no thresholds hard-coded in TypeScript), imports its sources for `context.cities`, computes every cell of `context.snapshotId`, writes with `writeCategoryScores`, and returns `{ sourceDates }` (for example `{ osm: '2026-11-01', urban_atlas: '2021' }`). Cells without data get `score: null`, never a made-up value.
4. Register the module in `src/scoring/registry.ts`. Modules run in registry order; a module must not depend on another module's output except through tables the earlier module documents.
5. Run it for one city: `pnpm --filter @propertyscore/worker start build-snapshot --city timisoara --score <key>`.

Modules are idempotent: running a snapshot twice overwrites, never duplicates. Big source files (OSM extracts, GeoPackages) are cached under `SOURCES_DIR`, never stored in the database; only the derived rows are. The one exception is `private.transit_routing_bundles`: the report runs where the snapshot's `SOURCES_DIR` volume is not mounted, yet must route on exactly the network the score used, so each snapshot keeps its OSM clip and GTFS archives there as `bytea` (about 20 MB of clip and 10 MB of GTFS for București, so roughly 70 MB per snapshot across the nine cities and about 140 MB while two snapshots coexist). A private Storage bucket is the alternative if this outgrows the database. The service that generates reports therefore needs Java 21 and r5py like the snapshot job.

## Report sections

`generate-report --report <id>` turns a `pending` or `failed` row of `public.online_reports` into a `ready` one: `private.begin_online_report` checks the ready snapshot and finds the address's cell (codes `report_not_found`, `report_already_ready`, `no_ready_snapshot`, `outside_coverage`), the sections run, and `private.complete_online_report` freezes `result` (the sections plus `summarize_report_zone`: zone and per-category score, percentile among residential cells, city average, histogram, weights, source dates) with the snapshot and formula version. Any failure goes to `fail_online_report` with the error code, except `report_already_ready` and `report_in_progress` (a row another run has been generating for less than 15 minutes; after that it counts as stuck and can be started again).

- `begin_online_report` does not check payment: it accepts `pending_payment` rows so `create-report` works before the order flow exists. The order flow must move a report out of `pending_payment` only after the payment is confirmed and only then queue `generate-report`.

- A score that shows more than its number in the report adds a `ReportSection` (`key`, `build(context)`) in `src/scoring/<key>/<key>.report.ts`, returning a JSON object built from its own tables for the report's cell and snapshot (or `null` when there is nothing to show), and registers it with one line in `src/report/sections.ts`. The object lands in `result.<key>`, where the report page will read it once it is built.
- Every section starts with `schema_version: 1` and `status: 'scored' | 'no_data'`.
- A context indicator is a section without a score: its key is a `ContextKey` (`src/scoring/categories.ts`, today `seismic` and `investment`), never one of `CATEGORY_KEYS`, so it has no `ScoreModule`, writes nothing to `cell_scores` and never enters `overall`. Its `status` is `'context' | 'no_data'` (with a `reason` code when there is no data), and its data comes from its own `private` tables, read at the address when the report is generated. The context carries `reportId`, so a section can read the declared details of `online_reports` (`declared_area_m2`, `declared_rooms`).
- `readCellCategory` (`src/report/cell-category.ts`) returns the cell's score, `inputs.<key>` and city; `sectionParams(params, key)` picks `params.<key>` from the frozen formula. The context also carries `router` (the Valhalla client, `null` without `VALHALLA_URL`), so a section can route from the exact address.
- Sections registered today: `safety` (day and night of the cell, the waterfall at the address from `scoreAtPoint`, the nearest police, fire station, non-stop, embassy and station; with `router` its walking types are walked from the address, entered at their nearest edge), `accessibility` (components, the cell's stops with their lines, the busiest lines at peak and the trips to `key_destinations` from `cell_transit`, with walk, wait, ride and line planned from the address by `planTripsFromAddress`), `fifteen_minute` (`buildFifteenMinuteReport`: categories, groups, places, isochrones), `green`, `noise` (`assessNoiseAtAddress` plus the display bands and map radius; `map.heat` is the day level on a 50 m grid within `map_clip_m` of the address (`center`, `step_m`, `half`, row-major `levels` from the north-west corner, null outside the circle), computed by `noiseHeatGrid` from the same `assessPoint` formula; the PDF draws it as a smooth gradient in the page, `map.bands` stays optional for the example file), `air` (the 12 monthly means, limits, verdict and city average from `cell_air`), `industry` (`buildIndustryReport`), `education` (levels and the nearest institutions with walking distance from the address), `health` (the five layers with their nearest place) and the context sections `seismic` (the P100-1/2013 `ag` of the zone at the address and of each city's centre from `private.seismic_zones`, its hazard level from `params.seismic.levels`, `precision` `address` or `city`) and `investment` (asking price and rent around the address from `private.market_listings`, or for the whole city from `private.market_area_statistics`, see below).
- Section output is frozen with the report: the frontend never queries the engine tables. Keep it small (the nearest features, a few measured values), never source geometries.
- `create-report --email <user> --lat <lat> --lon <lon> --address <text> [--locale ro|en]` inserts a pending report for a local user; it stands in for the order flow and is for local testing only.

## Health source imports

`import-health-sources [--dir <path>] [--city <slug> …] [--valid-from YYYY-MM-DD]` fills the two reference tables the Health score reads, from files in `--dir` (default `SOURCES_DIR/health`). It runs before `build-snapshot`, never inside it.

- `cnas/<city slug>/surse.csv` (`fisier,tip,data_listei,url_pagina,url_fisier,observatii`) lists the files of each CAS list as published; `tip` is `farmacii`, `medici-familie`, `ambulatoriu`, `spitale` or `dentist`. Each `.xlsx` (up to the fifth sheet, for workbooks that open on a pivot), `.xls`, `.csv`, `.html` or `.pdf` file is read by `readProviderTable` (for a PDF, the column split that fills the most rows with both a name and an address) and `findTableColumns` (header row found by its provider name and address or locality columns), then `extractCnasProviders` keeps the city rows: by the locality column, where `Sector 1`–`6` counts as București and an empty cell falls back to the address, or, without one, by the city name in the address (county mentions such as `jud. Iași` ignored; București lists are not filtered); duplicates dropped, then `private.replace_cnas_providers` replaces that city, kind and list date with the rows of all its files together (a list with a file that cannot be read keeps its previous import). Addresses are geocoded later, by the snapshot. Other formats are logged and skipped. PDF columns are rebuilt from the text layout, so a PDF list is best effort: an address can carry the text of a neighbouring column.
- `upu-cpu.csv` (`oras,nume,nivel,pediatric,adresa,lat,lon,sursa_act,sursa_url`) is the list of hospitals with UPU or CPU. A row without coordinates is placed by the offline geocoder; when one row of a city cannot be placed, that city's units are left as they are. `private.sync_emergency_hospitals` keeps the open units that did not change (same name, level, pediatric flag, within 100 m), closes the others on `--valid-from` (default the first day of the current month) and opens the new ones then. A city with no row in the file keeps its units.

## Investment context (market listings)

- Listings come only through `import-market-listings --source <code> --period YYYY-MM --file <csv> [--eur-ron <rate>]`, one CSV per source and month in a fixed contract (`MARKET_CSV_COLUMNS` in `src/scoring/investment/market-import.ts`): a provider's format is mapped to it before the import, never read directly. The worker never reads listings from a site: the only pages it requests are the statistics pages below, under their publisher's written agreement.
- An import is a `private.market_imports` row (unique per source and file SHA-256, so the same file is refused with `market_import_exists`) and its rows in `private.market_listings`, append-only. Rows are cleaned with `params.investment.plausible`, duplicate ids in the file are dropped, and rows more than `city_buffer_m` from every covered city are not stored; the counts land in `market_imports.rejected`. An interrupted import is started again from scratch with the same command.
- A report reads only the imports completed before its snapshot's `finished_at`, each listing as the latest of those imports saw it (`private.market_observations`), so a report generated again from the same snapshot gives the same figures. The formula (`investment.formula.ts`) dedupes listings across sources, drops Tukey outliers, widens the radius through `radii_m` until `sale_min_count` / `rent_min_count`, and falls back to the city summary.
- Averages a source publishes per city and month (a monthly asking-price index, a rent report) come through `import-city-averages --source <code> --file <csv> [--eur-ron <rate>]`, in the contract `CITY_AVERAGE_CSV_COLUMNS` of `src/scoring/investment/city-averages-import.ts`: `city` (slug), `period` (`YYYY-MM`), `transaction`, `property_type`, `rooms` (empty for every size, `3`, or `4+`), `price_m2` and/or `price_month` (a sale has only `price_m2`), `currency`, `source_url` (optional `https://` link shown with the figure). One file may hold several months, so a year of history can be loaded at once. The import is a `market_imports` row with `content = 'city_averages'` and its rows in `private.market_city_averages`; rows of unknown cities, duplicate keys and prices outside `params.investment.plausible` are counted in `rejected`. The file is filled by hand from figures the source allows us to reuse; sources read automatically go through `import-market-statistics` instead.
- Statistics a source publishes per city and zone are read once a month by `import-market-statistics [--source <code> …] [--city <slug> …] [--period YYYY-MM] [--retry]` (`src/scoring/investment/area-statistics-import.ts`), one `market_imports` row per source with `content = 'area_statistics'` and its rows in `private.market_area_statistics`: the whole city (zone null) or one zone, every size or one rooms band, with the medians, the p25–p75 interval, the listing and distinct-apartment counts the source gives, `observed_on` (the day the source states, null when it dates the figure only by month) and `source_url` (the page or index to cite). Figures are asking prices, never transactions. Rows outside `params.investment.plausible`, without a median or repeated are counted in `rejected`. `median_area_m2` is the median area of the listings when the source gives it, and `is_nearby_locality` marks a zone that is a separate locality next to the city (the `NEARBY_LOCALITIES` of `imospot.ts`, by county and name: Dumbrăvița, Giroc, Moșnița Nouă and Ghiroda for Timișoara; Șelimbăr, Cristian, Cisnădie and Șura Mică for Sibiu), not a neighbourhood. `private.market_area_statistics_at(city, cutoff, from)` returns, for each source, its latest import completed before the cutoff, and `private.market_city_sale_history(city, cutoff, from)` the whole-city sale median of every month and source.
- Sources (`MARKET_STATISTICS_SOURCES`; a new one needs its publisher's licence or written agreement first, recorded in the PR): `apartamente_org` (the city and zone statistics pages of apartamente.org, sale and rent: the `Dataset` JSON-LD, the typical interval, the rooms table and the zone links of the city page), `apartamente_org_index` (its monthly index CSV, city rows only) and `imospot_index` (the Indicele Imospot CSV, cities and București neighbourhoods; apartments only). The statistics are CC BY 4.0. The index sources try the current month's edition, then the previous one.
- The written agreement of apartamente.org (2026-11-17) is enforced in code and must stay so: only paths under `/apartamente-de-vanzare/` and `/apartamente-de-inchiriat/` of the nine cities in `APARTAMENTE_ORG_CONSENTED_CITIES` plus `/raport-piata/<YYYY-MM>.csv` (never listings, search or the site's API); a `User-Agent` of `PropertyScore/1.0 (+<MARKET_SOURCE_CONTACT>)`, never a browser's; one request at a time, at least 2.5 s after the previous answer, through `createPoliteClient` (`src/sources/polite-client.ts`), which reads `robots.txt` first and refuses a disallowed path; once a month: each source gets a row in `private.market_statistics_runs` for the calendar month before its first request, and a source with a row is not read again that month, whether the run imported, found nothing new or failed. `--retry` reads it again and is a person's decision after looking at the failure, never part of a schedule (the future Railway service has restart policy `NEVER`). A 429, or a `Retry-After` longer than two minutes, stops the source at once (`source_asked_to_stop`); a shorter `Retry-After` (seconds or a date) and the `Crawl-delay` of `robots.txt` are waited out; an unreadable `robots.txt` means no page is requested. A zone page that redirects to its city or answers 404 is a zone without data (`zone_without_data`), never followed. More cities, other data or another frequency need their answer first. Never add imobiliare.ro, Storia, OLX or Publi24: they refused or forbid it.
- `--period` reads a past edition, to fill the monthly history once: only for the `PAST_EDITION_SOURCES` (`imospot_index`); any other source is refused with `past_edition_not_agreed`, by the command line and again by `importAreaStatistics`, because the apartamente.org agreement covers one reading a month of the current figures. A past month reads exactly the edition asked for (`source_edition_missing` when it does not exist, never the month before), and that month is its row in `market_statistics_runs`.
- When the listings give no sale figure, the report section reads these statistics before the city averages (`assessCityStatistics` in `investment.city-statistics.ts`), for the whole city only: zones have no geometry, so an address is never matched to one. The blocks have `precision: 'city_statistics'` and `price_kind: 'asking'`, each with its `source` (code, month, `observed_on`, link). `sale`: the median €/m², the P25–P75 interval and the listing count of one source: among the sources of the newest month, the first in `MARKET_STATISTICS_SOURCES` order that publishes an interval for every size (a source with only a median otherwise, with a null interval); an older month never wins over a newer one, `typical` (median area and price of a listing, when the source gives the area) and the estimate for the declared area with its low and high bounds (rounded to 1,000 €). `rent`: the city's median rent and €/m² per month, with `basis` `per_m2` when the source publishes the €/m², `median_over_area` when it is the median rent over the median area (a derived figure the frontend labels as such) and `all` when only the median rent is known, and the estimate for the declared area (rounded to 5 €). `yield.gross_pct` is 12 × rent €/m² ÷ sale €/m², the city's figure: the sale €/m² is the one the rent's source publishes for the same month, or the `sale` block's when it is of the same month as the rent; a sale and a rent of different months give no yield, and neither does a rent without a figure per square metre. `yield.city_gross_pct` stays null, because the figure already is the city's. Nothing else is compared across sources. `nearby`: up to 3 localities next to the city, the busiest first. `history`: the months of one source (the sale's when it has at least 2), at most 12, null under 2 months; a month the source did not publish is simply absent, and its link is the index page, not an edition. The figures per square metre are always written, so the frontend can recompute the estimates for another area. Nothing is derived that the sources do not publish: no radius, histogram or days listed.
- These statistics are read as they were when the report was created (`online_reports.created_at`), not at the snapshot's `finished_at`: they are published monthly figures, independent of the scoring grid, and a snapshot built before the month's import would otherwise show no data until the next snapshot. A report generated again gives the same figures, because its creation time does not change; listings and city averages keep the snapshot cutoff.
- `MARKET_SOURCE_CONTACT` (an email address, `contact@propertyscore.ro` in production) is required by this command only and is sent to the sources in the `User-Agent`. A full run is about 480 requests and 25 minutes. `--city` is for local checks: it completes the month's import for that source with only those cities.
- When the listings give no sale figure (no import, or too few listings in the city), `assessCityAverages` (`investment.city-averages.ts`) reads `private.market_city_averages_at` (the latest import before the snapshot's `finished_at` for each source, month and rooms band) and writes blocks with `precision: 'city_average'`, each with its `source` (code, month, link): the asking €/m² for the declared rooms band (or every size), its change against the same month a year earlier, the estimate for the declared area, the rent (`same_rooms`, `per_m2` or `all`), and the gross yield and the city's yield only when the sale and rent figures are of the same month. The listing sources stay in `sources` when too few listings sent the report to the averages. Only apartments are read, like the listings. Averages whose month ended more than `window_days` before the snapshot are ignored. The radius, the P25–P75 interval, the histogram and the days listed are never derived from averages.

## Working on several scores in parallel

Each score is built on its own branch on top of the foundation; these conventions keep the branches from colliding.

- **Shared files you may touch:** one line in `src/scoring/registry.ts` (modules listed in the order of `CATEGORY_KEYS`), one line in `src/report/sections.ts` for the score's report section, new `apt-get` packages appended to the single install line of `worker/Dockerfile`, new variables in `src/config/env.ts`. Changing `ScoreContext`, `ScoreModule`, `writeCategoryScores`, the orchestrator or the foundation tables goes through the foundation owner (the Green thread) in its own PR.
- **Migrations:** `supabase migration new <verb>_<object>` at the time you write it; the timestamp order between scores does not matter because no score migration depends on another. Add parameters only to your own key, on the active online version (`v3` since `recalibrate_noise_scale`): `update public.scoring_versions set params = params || jsonb_build_object('<key>', …) where kind = 'online' and is_active`. That works only while no snapshot uses that version; once one did, the freeze trigger refuses, so insert a new version copied from the active one with your keys added, set `is_active = false` on the old one and activate the new one in the same migration (the pattern of `add_building_details_to_reports`). Keys added this way are optional in the score's Zod schema, so reports on older snapshots keep working.
- **Schema:** score tables, enums and functions go in `private`, so `database.types.ts` does not change and the branches do not conflict on it. pgTAP files are named `supabase/tests/scoring_<key>.test.sql`.
- **`is_residential`** belongs to the foundation: the orchestrator sets it from OSM land use (`src/snapshot/residential.ts`) before the modules run. Modules never write it.
- **`poi_features`** is shared: insert with `on conflict (snapshot_id, source_ref, category) do nothing`, use your own `category` codes and never delete rows of another category. The 15-minute thread owns the common categories (shops, schools, clinics, transit stops).
- **Walking distance:** the 15-minute thread owns the pedestrian routing (Valhalla, exposed as `context.router`, `null` when `VALHALLA_URL` is unset). When the router is `null`, use the straight-line distance times `params.<key>.walk_detour_factor` and record `distance_method: 'straight_line'` in `inputs.<key>`, so the report shows an approximate value.
- **Source dates:** `sourceDates.osm` is `osmExtractDate(extractPath, context.period)`, the replication date of the extract; other sources use their edition (`urban_atlas: '2021'`).
- **No data:** a cell without usable source data gets `score: null` and `inputs.<key>.reason` (a `snake_case` code such as `no_source_data`), never a guessed value.
- **City figures** beyond the shared ones go under `score_snapshots.stats.<key>.<city slug>`, written with `stats = stats || jsonb_build_object('<key>', …)`.

## Commands and tests

```
pnpm --filter @propertyscore/worker start build-snapshot [--period YYYY-MM] [--city <slug> …] [--score <key> …]
pnpm --filter @propertyscore/worker start generate-report --report <uuid>
pnpm --filter @propertyscore/worker start render-report-pdf --out <file.pdf> (--report <uuid> | --input <file.json>)
pnpm --filter @propertyscore/worker start create-report --email <user> --lat <lat> --lon <lon> --address <text> [--locale ro|en]
pnpm --filter @propertyscore/worker start import-health-sources [--dir <path>] [--city <slug> …] [--valid-from YYYY-MM-DD]
pnpm --filter @propertyscore/worker start import-market-listings --source <code> --period YYYY-MM --file <csv> [--eur-ron <rate>]
pnpm --filter @propertyscore/worker start import-city-averages --source <code> --file <csv> [--eur-ron <rate>]
pnpm --filter @propertyscore/worker start import-market-statistics [--source <code> …] [--city <slug> …] [--period YYYY-MM] [--retry]
pnpm test:worker          # worker Vitest suite; the database tests run when DATABASE_URL is set
```

- Unit tests sit next to the source (`*.test.ts`) and import from `vitest` explicitly.
- `render-report-pdf` writes the PDF of one report to a file and nothing else: no Storage upload, no row change. `--report` reads a `ready` row (codes `report_not_found`, `report_not_ready`); `--input` reads the same fields (`number`, `address_text`, `latitude`, `longitude`, `generated_at`, `result`) from a JSON file, so the document is rendered without a database or `DATABASE_URL` (`src/report-pdf/fixtures/example-report.json`: the real zone summary of one Timișoara address with example chapter details). Chromium comes from `CHROMIUM_PATH` (the image sets it; unset, Playwright's own browser is used). The maps load their tiles from `tiles.openfreemap.org` while rendering, the only host the page may reach. The document is Romanian only.
- A new document type gets its own folder beside `src/report-pdf/` and calls `renderPdf`; `src/pdf/` stays free of any document's content.
- Tests that need the database use `describe.skipIf(!process.env.DATABASE_URL)`, run against the local stack only, and remove the rows they created (snapshots, and the grid cells of a city when it had none before). Test files run one at a time (`fileParallelism: false`) because only one snapshot can be building. CI runs them after `pnpm db:test` with the local stack's URL.
- A test that builds a snapshot gets its OSM data from a small `.osm` fixture in `src/sources/fixtures/` through `prepareSourcesDir`, never from the network.
- Tests that need `osmium`, GDAL, `xls2csv` or `pdftotext` use `describe.skipIf` on their presence; CI installs `osmium-tool`, `gdal-bin`, `catdoc` and `poppler-utils`.

## Deploy (Railway)

The services are created and changed through the Railway connector or the dashboard, only after the user approves the exact list, and the settings below are their source of truth: a change on Railway lands here in the same PR. Railway Config as Code (`railway.json`, `railway.toml`) is deprecated and new services cannot use it; Railway Infrastructure as Code (`.railway/railway.ts`) needs the `railway` npm package, a dependency not added yet.

One Railway project `propertyscore`, environment `production`, region `europe-west4` (next to the Supabase project in `eu-central-1`). Nothing has a public domain: the worker reaches Valhalla over the private network.

- Railway starts `snapshot` only on its schedule (UTC) and skips a run while the previous one is still active, so the command must exit when done: `main` closes postgres.js, waits for stdout to flush and then calls `process.exit` with the command's outcome, because a handle left open by a source download or a child process otherwise keeps the container running after the last log line (the first Timișoara snapshot stayed active, idle, after `build-snapshot done`). `railway cron run` starts one outside the schedule.
- `snapshot` is created only once the migrations it needs are live in production through `deploy.yml`, and its first run is checked in the logs and in `score_snapshots`.
- `snapshot` has no volume: a cron container is not running between runs, so nothing can be uploaded to one, and the Hobby plan caps a volume at 5 GB. The files the worker reads but does not download (the EEA 1 km maps under `SOURCES_DIR/air/eea-maps/`) are therefore absent on Railway, and that score uses its documented fallback until the files get a path in the `source-extracts` bucket; the SIIIR schooling plan is read from the bucket through `SOURCE_MIRROR_URL`.
- Geofabrik refuses connections from Railway (and from other cloud hosts), so neither service can download the extract there. Each month the user downloads `romania-latest.osm.pbf` on their own machine and puts it in two places. For `snapshot`: over `osm/romania-latest.osm.pbf` in the private Storage bucket `source-extracts`, with content type `application/octet-stream` (the only type the bucket accepts; a browser gives `.pbf` files an empty type, so set it explicitly) (migration `create_source_extracts_bucket`, no policies, so only a secret key reads it; the project's global file size limit in Storage settings must stay above the extract, about 330 MB in 2026). For `valhalla`: with `railway volume files --volume valhalla-tiles upload <file> /romania-latest.osm.pbf --overwrite`; the upload goes through the running container. Before the monthly snapshot, upload the new extract over the same file, set `force_rebuild=True` (the variable change redeploys and rebuilds the tiles and `valhalla_tiles.tar` in a few minutes), then set it back to `False` once the build is done. The snapshot records `tilesetDate()` so a stale tileset is visible.
- Report and document jobs (`generate-report` after a payment, `render-report-pdf` and later documents) get their own service from the same image, with its own start command, once the hand-off from the order flow exists (`.claude/rules/architecture.md` §3).
- Generated documents are stored in Supabase Storage (a private bucket created by a migration, served through signed URLs), never on a Railway volume or bucket: their access follows the owner's RLS like every other file.
- System tools the worker shells out to (`osmium-tool`, `unzip`, `python3`, `gdal-bin`, `catdoc`, `poppler-utils`) and `chromium`, which `playwright-core` drives for PDFs, are installed in the `Dockerfile`, pinned by the base image's Debian release.
- The transit routing stack is also in the image: Java 21 copied from `eclipse-temurin:21.0.12_8-jre-noble`, the `/opt/transit` venv with `r5py` 1.1.7 from `worker/transit/requirements.txt`, and the R5 jar r5py downloads and checksum-verifies during the build (cached under `XDG_CACHE_HOME=/opt/cache`). The Temurin JRE runs on the bookworm base (glibc 2.36); the first Railway build is the check that the jar download works.
- Migrations reach production only through `deploy.yml`; deploy the worker after the migrations it needs are live.
